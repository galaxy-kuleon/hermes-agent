# Round 22 Lane Chooser + FTA3716 Failure Characterization — 2026-06-10

## Implemented: XA Lane Chooser

Added a first version of an automatic XA lane chooser to `pdfdocx5.py`:

```bash
--xa-strategy default     # previous single-lane behavior
--xa-strategy overlap099  # pdf2docx line_overlap_threshold=0.99 + preserve candidate layout
--xa-strategy auto        # run default_recovery and overlap099, pick lower QA score
```

`--xa-strategy auto` runs two XA candidates:

1. `default_recovery`
   - normal pdf2docx settings
   - normalize tables
   - recover missing text
2. `overlap099`
   - `line_overlap_threshold=0.99`
   - `preserve_candidate_layout=True`
   - no plaintext recovery fallback

The winner is copied to the requested output path, and the report records:

```json
{
  "xa_strategy": "auto",
  "selected_xa_lane": "overlap099",
  "xa_strategy_candidates": [
    {"lane": "default_recovery", "score": 40, ...},
    {"lane": "overlap099", "score": 6, ...}
  ]
}
```

### Human Contact-Sheet Finding

FTA3716 is not the same problem as the HK overlap-heavy forms.

For `overlap099` turn 1:

- rendered page count = 6 for 3 source pages
- rendered page 1 contains header/footer frame
- rendered page 2 contains the product table for source page 1
- rendered page 3 contains header/footer for source page 2
- i.e. each source page is split into two rendered pages

For compact turn 5:

- page count returns to 3
- but the main product table visually disappears/collapses
- rendered page only shows top/header/legal text bands
- visual ink height drops to ~0.28 of source

So the current compact-on-overflow adapter is destructive for this class: it fixes page count by crushing/removing the central table area.

### Root Cause Direction

Need a new adapter for repeated commercial/shipping documents:

```text
repeated-commercial-section / split-page-merge adapter
```

It should preserve the source page's product table and merge the two rendered halves per source page, instead of blindly compacting vertical density. Likely deterministic steps:

1. Detect split-page pattern: rendered_pages == source_pages * 2 and pages alternate header/footer vs central product table.
2. Do not choose compact profiles that destroy ink height.
3. Reorder or merge candidate OOXML elements so each source page keeps:
   - header/destination block
   - product line table
   - totals/payment/delivery/footer block
4. Use PyMuPDF source table bboxes to assign top/product/bottom regions.

This remains open and is the next meaningful target after lane chooser.
